| 位 | 名称 | 官方描述 |

| 24 | UNALIGNED | 未对齐访问 |
| 25 | DIVBYZERO | 除零 |

| 位 | 名称 | 含义 |
|---|---|---|
| 30 | FORCED | 有别的故障**升级**成了 HardFault（因为那类故障的异常被关闭） |
| 1 | VECTTBL | 取向量时总线错误 |
| 31 | DEBUGEVT | 调试事件 |

## 阶段一：把"故障码"翻译成人话

### T1 —— 手拆故障码

**【做什么】** 对着表 A / B / C，把 `CFSR = 0x00040000`、`HFSR = 0x40000000` 拆开：哪一段、哪一位、这一位叫什么。
**【线索】** 先判断"属于哪个位段"，再在段内数位号（写成 `2^N` 的形式再对位号，比直接数十六进制靠谱）。
**【自检 / 预期结果】**
- 你能说出：`0x00040000` 落在**哪一段**、是**第几位**、这一位的名字；
- 你能用一句话回答 HFSR 那位在说什么（"它本来是另一类故障，因为……所以升级成了 HardFault"）；
- 你能用**一句人话**概括"CPU 当时想做什么动作、但做失败了"。这句话将成为后面所有任务的锚点。

### T2 —— 从"故障名"锁定"是哪条指令"

**【做什么】** 故障名里出现了一个关键词（`EXC_RETURN`）。请回答：**什么指令会让 CPU "用 EXC_RETURN 去装载 PC"？** 然后在 FreeRTOS 移植层（`port.c`，`portable/GCC/ARM_CM4F/` 目录下）把符合这个特征的指令**全部找出来**，连同所在函数列成表。
**【线索】**
- 这类动作在汇编里长得像 `bx <寄存器>`；但不是每一条 `bx` 都算 —— 只有 `bx` 到**特定格式的值**才会被 CPU 当成"异常返回"。
- 你想的是"任务怎么切换"这件事：切换上下文一共需要几种"返回"？启动第一个任务，和切换第 N 个任务，是同一个函数干的吗？
**【自检 / 预期结果】**
- 你列出的条数应为 **2 条**。如果你只找到 1 条，说明你漏了另一条换栈路径 —— 回去看 `port.c` 里另一个 `naked` 函数；
- 每条旁边能写清：**它的执行时机**（一次？每次？）和**它用的那个值是从哪里来的**。

## 阶段二：不烧录，把现场还原出来

> 这一阶段的目的是让你习惯一件事：**一半的故障不用烧板子就能查。** 你只需要会读二进制。

### T3 —— 确认异常入口"接对了人"

**【做什么】** 把 `firmware.bin` 前 16 个 32 位字打印出来，对照 `nm -n` 的符号表，填满 16 行：`向量号 | 名字 | 地址 | 属于哪个函数`。重点看 **3（HardFault）/ 11（SVCall）/ 14（PendSV）/ 15（SysTick）**。
**【线索】**
- 向量表第 0 项**不是函数地址**，它是初始栈顶（一个 RAM 地址），这本身也是一个要核对的信息；
- 表里所有函数地址的**最低位都是 1**（Thumb 标志位），取真实地址要 `& ~1`；
- 启动文件里这些符号是 **weak** 的，如果你没接管，它们会全部指向同一个 `Default_Handler`。
**【自检 / 预期结果】**
- 16 行填满，且你能回答：**若 [11] 指向 `Default_Handler`，现象会是什么样？**（把它写成一句话，T12 会用到）
- 你能说出 [15] 指向的函数**是哪个文件里的**（本工程的 SysTick 是共用的，这条很关键）。

### T4 —— 自上而下画出完整调用链

**【做什么】** 画一张表：**从上电到"第一个任务开始执行"**，把函数链写出来，每行填四列：`函数 | 谁调用它 | 它做了什么 | 它留下的关键副作用（改了什么寄存器/内存）`。
起点：`Reset_Handler`。终点：任务函数（`Task_Touch`）的第一行。
**【线索】**
- 链上会出现这些名字，但**顺序要你自己排**：`main` / `HAL_Init` / `SystemClock_Config` / `SystemInit` / `xQueueCreate` / `xTaskCreate` / `vTaskStartScheduler` / `xPortStartScheduler` / `vPortSetupTimerInterrupt` / `prvPortStartFirstTask` / `vPortSVCHandler` / `pxPortInitialiseStack`。
- 注意 `pxPortInitialiseStack` **不在**这条主线的时间顺序上 —— 它属于"任务创建"阶段的分支。请单独标出它的调用者。
- 有一个环节是**硬件**做的（不是函数）：一条 `svc` 指令 → CPU 自动跳到某个向量。
**【自检 / 预期结果】**
- 表里能明确区分**三个阶段**：① 任务被创建（数据结构建好，但还没跑） → ② 调度器接管 CPU → ③ 第一个任务被"返回"进去；
- 你能指出：**"任务创建"和"任务开始执行"之间，中间隔了很久**（中间还干了创建空闲任务、定时器任务、配置 SysTick 等事）；
- 你能回答：任务创建阶段写入的那个"初始栈帧"，在整个链条里**被谁读过一次**？（答出来，它就是 T2 里两条指令中的一条。）

### T5 —— 读懂那个"启动第一个任务"的函数

**【做什么】** 把 T2 里那个函数反汇编出来（`objdump`），**逐条注释每一条指令在干什么**。
**【线索】**
- 看 `ldmia`：它一次取了**几个** 32 位字？寄存器列表里最后一个是什么？（x86 思维会漏掉它）
- 看那条 `msr`：它把某个通用寄存器写进了哪个**特殊寄存器**？
- 看最后那条 `bx`：它用的寄存器是**从内存里取的**，还是 CPU 进中断时留下的？（这个区别是本案的分水岭）
**【自检 / 预期结果】**
- 你能用一段伪代码复述它：`读 TCB → 读栈顶指针 → 连续取 N 个字 → 第 N 个字装进 LR → 设置 PSP → bx`；
- 你能报出 **N = 9**，并说清"第 9 个字就是那个用来返回的值"；
- 你能回答：**如果这 9 个字里第 9 个是垃圾，`bx` 会发生什么？**（对照 T1 的结论 —— 你应该能自己把故障码和这条指令对上。）

### T6 —— 画"任务初始栈帧"布局表 + 交叉验证

**【做什么】** 读 `pxPortInitialiseStack()` 源码（`port.c`），**手推**它写了哪些字、每个字落在哪个偏移。产出一张表：`偏移(以"字"为单位) | 内容 | 谁写的 | 内容从哪来`。然后回答 T5 的读法落在表里的哪几行。
**【线索】**
- 函数是**从栈顶往下**写的（每写一个 `pxTopOfStack--`）。**从最后一次赋值开始倒着数**，比从第一行顺着数更不容易错。
- 注意有个偏移上写的是一个**常量**，它的作用是"告诉 CPU：返回时用哪个栈、带不带 FPU 现场"。
- 数完顺便看一眼：这个函数返回的指针，是不是 8 字节对齐的？异常入栈对栈指针对齐有什么硬要求？
**【自检 / 预期结果】**
- 表里应有 **17 行**；你能标出**哪一行是"异常返回控制字"**、它被写成什么常量；
- **交叉验证**：T5 读的 9 个字 ↔ 本表的哪个偏移区间，**对得上还是对不上**？
  - **对得上** → 好，说明"帧布局"**不是**本案嫌疑人。请在记录里明确写："假设 H1（帧布局不匹配）—— **排除**，理由：机器码与源码严格一致。"（这一步是整个训练最重要的习惯：**排查是排除法**。）
  - 对不上 → 那也是成果（"偏移错位"是一种具体故障），同样写清楚。

## 阶段三：形成假设 + 设计证伪实验 ★本次最值钱的部分

> 到这里为止你只做了"读代码"。能定位故障的分水岭在下面这三题。

### T7 —— 列出所有"能让那个值变错"的原因

**【做什么】** 假设 T5 里那个 `bx` 用到的值是错的。请列出**至少 3 类**可能原因。
**【线索】** 往这三个方向想：① 这个值**被写坏**了；② 这个值**没被写坏，但位置读错了**；③ 这个值写对了、位置也对，但**它和硬件的约定不一致**。
**【自检 / 预期结果】**
- 每一条假设后面，**必须**能回答一句："**我打算怎么观测它？**"
- **写不出观测手段的假设，直接划掉。**（这是纪律：能证伪的才叫假设，其余都是猜。）
- 你会得到一张表：`假设 | 观测手段 | 观测结果会指向什么`。这张表就是你后面的行动清单。

### T8 —— 把"观测点"放进固件

**【做什么】** 设计一个**在进调度器之前**执行的观测点：什么时机读、读**哪两个内存地址**、屏上显示什么格式、判定条件是什么。
**【线索】**
- 你要读的第一个地址：FreeRTOS 记录"当前任务"的那个全局指针（用 `nm -n` 能查到它的地址）；
- 你要读的第二个地址：**从第一个地址指向的结构体里再取一个字段**（提示：TCB 的**第一个成员**是什么？查 `tasks.c` 的 `struct tskTaskControlBlock`）；
- 别直接 `*ptr` 就解引用 —— 先判断地址落在 RAM 范围内（`0x20000000 ~ 0x2001FFFF`），否则故障处理器自己会再摔一次（**double fault**，那你就什么都看不到了）。
**【自检 / 预期结果】**
- 你能写出可编译的伪代码；
- 你能说出**两种结果分别指向哪个方向**："读到 A → 说明问题在 XXX 阶段；读到 B → 说明问题在 YYY 阶段"；
- 你能解释为什么要**在进调度器之前**读，而不是进之后。（提示：进去之后它可能被改写。这一步的目的是区分"建错了"和"被改坏了"。）

### T9 —— 一个"不烧录也能验证"的检查

**【做什么】** 针对 T7 里"配置类"的假设，设计一个**只看二进制文件**就能验证的方法。
**【线索】**
- 配置宏有两种命运：一种只影响编译期（比如栈大小），另一种**它的数值会被直接写进硬件寄存器**。你要找的是第二种。
- 方法：把一个关键函数的机器码反汇编出来，**看里面出现的常量**；再回到头文件看宏的实际数值，两边对一下。
- 找哪两个宏？提示：**和"中断优先级"有关，一个是内核自己的中断优先级，一个是临界区的屏蔽阈值。**
  （这两个名字你在 T4 的链里见过 —— `xPortStartScheduler` 配置 SysTick/PendSV 时用过一个，`vPortEnterCritical` 用过一个。）
**【自检 / 预期结果】**
- 你能在反汇编里找到**两个常量**（一个 `mov` 立即数、一个 `orr` 立即数）；
- 你能算出"硬件**实际生效**的优先级数值"，并发现它与"头文件里写的编号"**不相等**；
- ⚠️ **到这一步先别改代码。** 先回答：这个差值会让**哪一类运行时行为**变异常？（答不上来就说明 T10/T11 还得补。改代码之前必须能说出预期后果 —— 这是纪律。）

## 阶段四：底层原理（把"这一例"变成"这一类"）

### T10 —— 为什么"写进去的值"不等于"生效的值"

**【做什么】** 用位运算算清楚：往 NVIC 的 8 位优先级寄存器写 `0x00 / 0x0F / 0x50 / 0xF0`，硬件**读回来**分别是多少？对应**优先级编号**分别是几？
**【线索】**
- 前提事实：STM32 的 NVIC 优先级寄存器是 8 位，但**只实现高 4 位**（`bit7:4`），低 4 位读出恒为 0。
- 所以"优先级编号 n"要写进寄存器，必须写成 `n << 4`。
**【自检 / 预期结果】**
- 你能列出四行对照表：`写入值 → 实现位 → 实际优先级编号`；
- 你能指出**哪两个不同的写入值会被硬件认为是同一个优先级**（就是这一对造成了本次故障）；
- 你能写出一条通用规则：「优先级编号 → 寄存器值」的换算公式是什么（用 `configPRIO_BITS` 表示）。

### T11 —— 为什么"内核中断必须最低优先级"

**【做什么】** 回答链条：如果 PendSV 被配到了优先级 0，而临界区用的是 `BASEPRI = 0x50` —— ① 一次 `taskENTER_CRITICAL()` **能挡住 PendSV 吗**？② 挡不住会破坏什么？
**【线索】**
- `BASEPRI` 的语义是"屏蔽**数值上大于等于**它的优先级"。算一算：优先级 0 的"数值"是多少？`0x50` 能盖住它吗？
- 再想一层：`xQueueSend` 内部用临界区保护的是什么？（去看 `prvCopyDataToQueue` / 就绪链表操作）
- 如果切换正好发生在"指针改了一半"的瞬间（比如链表刚摘下来、还没插到新的地方），下一个任务切回来时会看到什么？
**【自检 / 预期结果】**
- 你能画出一条**具体时序**：在哪个 API 的哪两步之间插进一次 `PendSV` → 哪个变量/链表被写坏 → 现象是什么（数据错乱？队列丢数据？还是直接挂？）；
- 你能说出**两条**"内核中断必须最低"的理由（一条关于临界区，另一条想 `xPortSysTickHandler` 内部那句 `portDISABLE_INTERRUPTS()` 到底想挡住谁）。

### T12 —— 为什么"静默"才是最贵的学费

**【做什么】** 回答三个"如果没有这个工具会怎样"，并给出结论：
1. 不定义 `configASSERT` 时，FreeRTOS 内部的参数检查会怎样？
2. 不接管 `HardFault` 向量时，CPU 触发故障后会做什么？
3. 本板 PC0 LED 是坏件 —— 这件事对"调试输出策略"意味着什么？
**【线索】**
- `configASSERT` 在 FreeRTOS 头文件里有个"默认定义"，去看它是什么；
- 启动文件里 `HardFault_Handler` 是 `weak` + `.thumb_set ... Default_Handler`，去看 `Default_Handler` 的机器码（就一条指令）；
- 想"信息论"层面的事：**故障发生时，你的系统还能不能"说话"？有几种通道可以说话？**
**【自检 / 预期结果】**
- 你能说出"三根天线"（断言 / 故障向量 / 屏幕）各自把**哪一类**错误从"静默"变成"可读"；
- 你能给出自己项目的**优先级排序**：先接哪一根、为什么（结合"本板 LED 坏"这个约束）；
- 你能回答一个反向问题：**为什么 `configASSERT` 默认是空宏？**（想"生产环境 vs 调试环境"的取舍）

## 阶段五：迁移演练

### T13 —— 换一个症状，独立跑一遍

**【做什么】** 这次**不给你任何答案**。场景：

> 同一块板、另一个工程。现象是：**任务能正常跑起来，但偶尔莫名卡死、或显示数据错乱；复位后时好时坏，十几分钟才出一次。**

请写一份**排查计划**（不是答案）：
1. 你会先读哪个寄存器？怎么判断"是不是硬件异常"？
2. 如果怀疑"中断优先级配错"，你的**验证路径**是什么？
3. 如果怀疑"栈溢出"，你的验证路径是什么？
4. 怎么把"偶尔"变成"必然"？（**可复现是定位的前提** —— 想想怎么提高复现概率：改延时？加日志计数器？改负载？）
5. 你会给固件加哪 2~3 个"观测点"？分别想观测什么？

**【线索】** 复现策略的思路：让"可疑的时序窗口"变大 —— 比如把中断频率调高、把临界区变长、让两个任务的优先级更接近。
**【自检 / 预期结果】**
