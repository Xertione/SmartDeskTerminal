# VS Code 手动调试实操手册（PIO Debug · 手动挡）

> **适用范围**：本工程 `SmartDeskTerminal_freertos/`（STM32F407VET6 + PlatformIO + ST-Link V2）  
> **定位**：全程**手动**——只靠点菜单、点按钮、在面板里手打表达式。**不运行任何脚本**。  
> **为什么需要它**：`printf` 调试在裸机上很麻烦，而 SWD 调试器能直接"看进芯片里"。这三项技能（直读寄存器 / 采样引脚 / 读故障标志）是排查一切"程序行为不符预期"的基本功。  
> 最后更新：2026-09-18



---

## 0. 前置检查（1 分钟）

**操作目标**：确保调试会话能建立。

**软件 / 工具**：VS Code （打开 `SmartDeskTerminal_freertos` 文件夹）、ST-Link、板子（已上电）

**执行步骤**：

| # | 步骤                                                                            | 在哪操作        |
| - | ----------------------------------------------------------------------------- | ----------- |
| 1 | 确认左侧活动栏有 **PlatformIO** 图标（蚂蚁头）；没有就用 Extensions 装 `platformio.platformio-ide` | VS Code 活动栏 |
| 2 | 打开 `platformio.ini`，确认有 `upload_protocol = stlink` 和 `debug_tool = stlink` 两行 | 资源管理器       |
| 3 | ST-Link 的 USB 插电脑、SWD 四线接板子、板子 USB-C 供电                                       | 硬件          |
| 4 | **关掉其它可能占用 ST-Link 的程序**：STM32CubeProgrammer、另一个 VS Code 窗口的调试会话、正在跑的 Upload  | —           |

**预期结果**：板子上红色电源灯亮；`platformio.ini` 两行都在。

> ⚠️ **ST-Link 是独占资源**：同一时刻只能有一个程序用它。调试时不能同时点 Upload，反之亦然。

## 1. 启动调试会话（后面所有操作的入口）

**操作目标**：让 VS Code 通过 ST-Link 接管芯片，进入可暂停 / 可查看的状态。

**软件 / 工具**：VS Code → **Run and Debug** 视图

**执行步骤**：

| # | 步骤                      | 具体操作                                   |
| - | ----------------------- | -------------------------------------- |
| 1 | 打开 **Run and Debug** 视图 | 点活动栏第 4 个图标（带小虫+播放键）；或按 `Ctrl+Shift+D` |
| 2 | 在顶部下拉框选配置               | 点下拉箭头，会看到 4 个自动生成的配置                   |
| 3 | 按 `F5` 启动               | 或点绿色 ▶ 按钮                              |

**4 个配置怎么选**（都是平台自动生成的，别改它们）：

| 配置名                             | 含义                   | 什么时候用              |
| ------------------------------- | -------------------- | ------------------ |
| `PIO Debug`                     | 编译 → 烧录 → 进入调试       | 改了代码，要一条龙          |
| `PIO Debug (skip Pre-Debug)`    | 跳过预构建，直接烧录+调试        | 只改了 debug 配置时      |
| `PIO Debug (without uploading)` | **不烧录**，直接接管板子上现有的程序 | **只读芯片状态时用这个**（推荐） |
| `C/C++ Runner: Debug Session`   | 与本工程无关（另一个扩展生成的）     | 不要用                |

**预期结果**：

- 底部状态栏变橙色，顶部出现**调试工具条**
- 左侧出现 `VARIABLES` / `WATCH` / `CALL STACK` / `BREAKPOINTS` 面板
- 底部 `TERMINAL` 区域切到 **DEBUG CONSOLE**，出现类似 `Info : [stm32f4x.cpu] halted due to debug-request` 的字样
- **板子上的现象会变**：CPU 被暂停，原来闪烁/循环的动作会**停住**——这是正常的，不是坏了

**如果报错**（按这个顺序查，别乱试）：

| 报错关键字                            | 原因                              | 处理                                                   |
| -------------------------------- | ------------------------------- | ---------------------------------------------------- |
| `Please specify debug_tool`      | `platformio.ini` 少 `debug_tool` | 补上 `debug_tool = stlink`（本工程已补）                      |
| `Error: open failed` / `hla_swd` | ST-Link 没插好 / 被别的程序占用           | 重插 USB、关掉 CubeProgrammer 等                           |
| `Failed to launch GDB`           | 工具链没装全                          | PlatformIO Home → Platforms → 确认 ststm32 已 Installed |

## 2. 先认清 5 个面板（各干一件事）

| 面板                | 在哪                     | 干什么                                                             |
| ----------------- | ---------------------- | --------------------------------------------------------------- |
| **WATCH**         | 左侧 `Run and Debug` 视图里 | **最常用**。手打**表达式**（如 `(GPIOC->ODR)&1`），每次暂停自动刷新                  |
| **VARIABLES**     | 同上                     | 显示当前函数局部变量 + 全局变量（`uwTick`、`SystemCoreClock` 在 **Globals** 分组里） |
| **CALL STACK**    | 同上                     | 程序"从哪来"的调用链。**排查卡死/故障时先看这个**                                    |
| **BREAKPOINTS**   | 同上                     | 断点清单，可勾选启用/禁用                                                   |
| **DEBUG CONSOLE** | 底部面板                   | 手打**低级命令**（GDB / 字节级读内存），也能看程序的报错输出                             |

**调试工具条按钮**（顶部悬浮条，鼠标悬停会显示名字）：

| 按钮        | 快捷键             | 作用                  |
| --------- | --------------- | ------------------- |
| Continue  | `F5`            | 继续运行，直到下一个断点        |
| Pause     | `F6`            | **暂停**当前程序（采样时反复点它） |
| Step Over | `F10`           | 执行当前行，**不进入**被调用的函数 |
| Step Into | `F11`           | 执行当前行，**进入**被调用的函数  |
| Restart   | `Ctrl+Shift+F5` | 复位芯片重新跑             |
| Stop      | `Shift+F5`      | 结束调试，放开芯片（程序恢复运行）   |

**怎么加一个 WATCH 表达式**：`WATCH` 面板标题栏点 **`+`** → 输入表达式 → `Enter`。

## 3. 任务 A：调试器直读（读芯片内部状态）

**操作目标**：不靠"看现象"猜，而是直接读出芯片真实的时钟、GPIO 配置——这是判断"是软件没跑对，还是硬件坏了"的分水岭。

**软件 / 工具**：VS Code → `WATCH` 面板（主）、`DEBUG CONSOLE`（备）

### A-1 用 WATCH 读（推荐，纯点+打字，不用懂十六进制）

在 `WATCH` 里逐个 **`+`** 添加下列表达式（**原样照抄**，包括括号）：

| 表达式（照抄）               | 读的是                | 正常值          | 判读                            |
| --------------------- | ------------------ | ------------ | ----------------------------- |
| `(RCC->CR>>17)&1`     | HSE 晶振是否就绪（HSERDY） | `1`          | `0` = 外部晶振没起振                 |
| `(RCC->CR>>25)&1`     | PLL 是否锁定（PLLRDY）   | `1`          | `0` = PLL 没锁                  |
| `((RCC->CFGR)>>2)&3`  | 当前系统时钟源（SWS）       | `2`          | `2`=PLL，`0`=HSI，`1`=HSE       |
| `(RCC->AHB1ENR>>2)&1` | GPIOC 时钟是否开        | `1`          | `0` = 外设时钟没开，GPIO 写不动         |
| `GPIOC->MODER & 3`    | PC0 引脚模式           | `1`          | `0`=输入，`1`=输出，`2`=复用，`3`=模拟   |
| `GPIOC->OTYPER & 1`   | PC0 推挽/开漏          | `0`          | `0`=推挽                        |
| `GPIOC->PUPDR & 3`    | PC0 上下拉            | `0`          | `0`=无上下拉                      |
| `SystemCoreClock`     | HAL 算出的主频          | `168000000`  | 不是这个数 = 时钟树或 `HSE_VALUE` 宏有问题 |
| `uwTick`              | 1ms 心跳计数           | 暂停时**每次都在涨** | 不涨 = SysTick 中断没在跑            |

**怎么判断 `uwTick` 在涨**：连点 **`F6`（Pause）→ `F5`（Continue）→ `F6`**，看这个值是否每次都比上一次大（大约间隔越久涨得越多）。

### A-2 用 DEBUG CONSOLE 读原始地址（备用，学一层更底层的）

在 **DEBUG CONSOLE** 里手打命令（`x` = examine memory；`/1xw` = 读 1 个 word 按十六进制显示）：

| 想读什么                                                 | 手打命令                |
| ---------------------------------------------------- | ------------------- |
| RCC 的 CR / PLLCFGR / CFGR / CIR 四个寄存器                | `x/4xw 0x40023800`  |
| RCC 的 AHB1ENR                                        | `x/1xw 0x40023830`  |
| GPIOC 的 MODER / OTYPER / OSPEEDR / PUPDR / IDR / ODR | `x/6xw 0x40020800`  |
| 直接按名字读                                               | `print/x RCC->CFGR` |

> 若提示命令不识别，在命令前加 `-exec `，例如：`-exec x/4xw 0x40023800`

**预期结果**：控制台打印形如 `0x40023800: 03037f83 07405408 0000940a 00000000`——第 1 个数是 `RCC->CR`，第 3 个是 `RCC->CFGR`。

**记住这几个常用地址（背下来很值）**：

| 外设/寄存器                   | 地址           |
| ------------------------ | ------------ |
| `RCC->CR`                | `0x40023800` |
| `RCC->CFGR`              | `0x40023808` |
| `RCC->AHB1ENR`           | `0x40023830` |
| `GPIOC->MODER`           | `0x40020800` |
| `GPIOC->IDR`（引脚**实际**电平） | `0x40020810` |
| `GPIOC->ODR`（CPU 想输出的电平） | `0x40020814` |
| `GPIOC->BSRR`（置位/复位，写用）  | `0x40020818` |

## 4. 任务 B：采样引脚输出

**操作目标**：不接示波器、不用万用表，用调试器"隔一段时间看一眼"引脚电平，从一连串采样值里看出它在翻转。

**软件 / 工具**：VS Code → `WATCH` + 调试工具条（方法 1、2）；`DEBUG CONSOLE`（方法 3）

### 方法 1：反复暂停采样（最简单）

| # | 具体操作                                                                          |
| - | ----------------------------------------------------------------------------- |
| 1 | 在 `WATCH` 里加两个表达式：`(GPIOC->ODR)&1`（CPU 想输出的值）和 `(GPIOC->IDR)&1`（引脚**实际**读回的值） |
| 2 | 按 `F5` 让程序跑                                                                   |
| 3 | 心里数 1 秒，按 `F6` 暂停 → 看这两个值                                                     |
| 4 | 按 `F5` 再跑，数 1 秒，再 `F6` → 再看                                                   |
| 5 | 重复 5~6 次，**手抄**每次的值                                                           |

**预期结果**：本工程里 PC0 每 500ms 翻转一次，所以你会看到采样值在 `0 / 1` 之间交替出现，例如：

```
第1次: ODR=1  IDR=1
第2次: ODR=0  IDR=0
第3次: ODR=0  IDR=0
第4次: ODR=1  IDR=1
```

采样间隔越接近 500ms，交替越明显。

### 方法 2：断点 + 单步（最能看清"变化的那一瞬间"）

| # | 具体操作                                                               |
| - | ------------------------------------------------------------------ |
| 1 | 打开 `src/main.c`，找到 `HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_0);` 这一行    |
| 2 | 点这行**行号左侧的空白处**（gutter）→ 出现**红点** = 断点下好了；或在 `BREAKPOINTS` 面板点 `+` |
| 3 | 按 `F5` 运行 → 程序跑到这行**停下**                                           |
| 4 | 看 `WATCH` 里 `(GPIOC->ODR)&1`，**记下值**                               |
| 5 | 按 **`F10`（Step Over）** 执行这一行 → 再看 WATCH 里的值                        |

**预期结果**：第 4 步和第 5 步的值**一定相反**（`0 → 1` 或 `1 → 0`）。这就是"单步执行一次翻转"的直接证据，比任何间接推断都硬。

> 看完记得**删掉断点**（再点一次红点），否则程序会一直停在这行。

### 方法 3：手打命令采点（和"自动采点"等价，只是手打）

在 **DEBUG CONSOLE** 里反复手打：`x/1xw 0x40020814`，把每次打印的值抄下来。这本质上就是手动版采样，配合秒表能得到和方法 1 一样的结论。

### ⚠️ 一个关键概念：ODR ≠ 引脚实际电平

| 寄存器     | 含义                                 | 说明         |
| ------- | ---------------------------------- | ---------- |
| **ODR** | Output Data Register：CPU **想**输出什么 | 只是芯片内部的一个值 |
| **IDR** | Input Data Register：引脚上**实际**是什么电平 | 反映真实引脚状态   |

**为什么区分它很重要**：ODR 在翻转、只说明"芯片内部的输出级在动"；**如果引脚焊点虚焊或外部负载断线，ODR 照样翻，但外面的东西不动**。所以判断"外部器件为什么不响应"时，要同时看 ODR 和 IDR，必要时还得配万用表量实际电压。

## 5. 任务 C：读故障标志（HardFault / 异常）

**操作目标**：程序"卡死 / 复位 / 行为错乱"时，判断它**有没有发生过硬件异常**，以及是哪种。这些标志位是**粘滞的**（一旦置位就保持，直到被清除），所以事后读也能查出来——这是它最大的价值。

**软件 / 工具**：VS Code → `WATCH` / `DEBUG CONSOLE` + `CALL STACK`

### C-1 先看三个总标志

在 `WATCH` 里加：

| 表达式（照抄）             | 读的是                                | 正常值 | 判读                                                      |
| ------------------- | ---------------------------------- | --- | ------------------------------------------------------- |
| `SCB->CFSR`         | Configurable Fault Status Register | `0` | **非 0 = 发生过故障**（下面 C-2 查是哪一种）                           |
| `SCB->HFSR`         | HardFault Status Register          | `0` | 非 0 = 进过 HardFault；bit30 `FORCED`=1 表示是被"逼"上去的          |
| `(SCB->ICSR)&0x1FF` | 当前异常编号（VECTACTIVE）                 | `0` | `0`=线程模式（正常跑代码）；`3`=HardFault；`5`=BusFault；`15`=SysTick |

**预期结果（本工程）**：三个都应是 `0` / `0` / `0`（或非 0 但不是 3/5 的一瞬间值）。这说明**没有发生过任何硬件异常**。

### C-2 CFSR 非 0 时，逐位查是哪一类故障

`CFSR` 是三个子寄存器拼起来的：`MMFSR`(bit 7:0) + `BFSR`(bit 15:8) + `UFSR`(bit 31:16)。

| 位      | 名称          | 含义（最常见几条）                      |
| ------ | ----------- | ------------------------------ |
| bit 0  | IACCVIOL    | 取指令访问违例（跳到非法地址执行）              |
| bit 1  | DACCVIOL    | 数据访问违例                         |
| bit 9  | PRECISERR   | **精确总线错误**：访问了不存在的地址（空指针最常见）   |
| bit 10 | IMPRECISERR | 不精确总线错误（可能是晚到的写操作，需要读 BFAR 辅助） |
| bit 12 | STKERR      | 入栈失败（**栈溢出**的典型信号）             |
| bit 15 | BFARVALID   | 下面 `SCB->BFAR` 里的地址有效          |
| bit 16 | UNDEFINSTR  | 执行了未定义指令（跳到了数据区）               |
| bit 17 | INVSTATE    | 非法的 Thumb 状态（函数指针类型不对）         |
| bit 25 | DIVBYZERO   | 除零                             |


**再补两条**：`SCB->BFAR`（`0xE000ED38`，出错时访问的地址）、`SCB->MMFAR`（`0xE000ED34`）。当 `BFARVALID`/`MMARVALID` 置位时，这两个值直接告诉你"是访问哪个地址炸的"。

### C-3 抓到故障现场的两个纯手动手法

| 手法                    | 怎么做                                                           | 得到什么                                                    |
| --------------------- | ------------------------------------------------------------- | ------------------------------------------------------- |
| **断点抓 Error_Handler** | 在 `src/main.c` 的 `Error_Handler()` 第一行下断点（点行号左侧）→ 按 `F5`      | 命中 = 程序走进了错误分支；此时看 **CALL STACK** 就知道是谁调用过来的            |
| **暂停看现场**             | 怀疑卡死时按 `F6` → 看 **CALL STACK** 和 WATCH 里的 `(SCB->ICSR)&0x1FF` | 看到 `Default_Handler` / 非法地址 = 异常没被处理；`ICSR` 告诉你现在在哪个异常里 |

> 更进阶的还有"让调试器在 HardFault 发生时自动停下"（`vector_catch`），但那属于半自动配置，本手册按纯手动思路走上面两条。

### C-4 清掉标志（想重新观察"这次有没有故障"时）

在 **DEBUG CONSOLE** 手打：`set var SCB->CFSR = 0`，然后 `set var SCB->HFSR = 0`，再按 `F5` 跑一会儿回来重读——这样读到的才是**本轮运行新产生的**故障。

## 6. 结束调试（别直接关窗口）

**操作目标**：干净地放开芯片，让程序恢复正常运行。

**执行步骤**：点调试工具条的 **Stop（`Shift+F5`）**，或按 `Ctrl+Shift+P` 输入 `Debug: Stop`。

**预期结果**：状态栏橙色消失，工具栏消失，板子上的程序**恢复运行**（比如灯又开始闪）。

> 直接关 VS Code 窗口也可能残留占用；下次 Upload 若报 `open failed`，先确认没有遗留的调试会话。

## 附录 A：如果 VS Code 调试起不来（纯命令行兜底）

> 只在调试视图报错、又急着读寄存器时用。**这是一条手打命令，不是脚本**。

```bash
PLATFORMIO_CORE_DIR="C:/.platformio" "C:/.platformio/penv/Scripts/pio.exe" debug --interface=gdb
```

或直接用 PlatformIO 自带的 openocd 手动敲（读一次寄存器就走）：

```bash
"C:/.platformio/packages/tool-openocd/bin/openocd.exe" \
  -s "C:/.platformio/packages/tool-openocd/scripts" \
  -f interface/stlink.cfg -f target/stm32f4x.cfg \
  -c "init" -c "halt" -c "reg pc" -c "x/4xw 0x40023800" -c "shutdown"
```

**两个必须记住的坑**：

1. `-c "echo 文本"` 的文本要用花括号包起来且**括号配平**，否则 Tcl 会报错并**静默中断后面所有命令**。
2. `halt` 会暂停 CPU；只想读内存不改行为时，**不要 halt**（Cortex-M 支持运行中读内存）。

## 附录 B：表达式的"读法"速查

| 写法                   | 含义                                    |
| -------------------- | ------------------------------------- |
| `GPIOC->ODR & 1`     | 取 PC0 这一位的值                           |
| `(RCC->CR>>17)&1`    | 把 bit17 挪到最低位再取，读出来就是 0/1，比看一长串十六进制好懂 |
| `((RCC->CFGR)>>2)&3` | 取 bit3:2（两位的字段），值 0~3                 |
| `SCB->CFSR`          | 直接读整个 32 位值（想看具体哪一位就按 C-2 表对号入座）      |

## 附录 C：自己烧录（Upload）标准流程

### C-3 失败对照（只看这三条，别乱试）

| 报错关键词 | 含义 | 处理 |
| --- | --- | --- |
| `No STM32 device found` / `open failed` | ST-Link 没插好 / 驱动没装 / 被别的程序占用 | 重插 USB；确认设备管理器有 ST-Link；关掉所有调试会话 |
| 相关 warning 后编译通过但**固件没变化** | 构建目录进入「产物缺失但被认定已最新」的假完成状态 | 关掉 VS Code → 删掉工程里的 **`.pio`** 整个文件夹 → 重开工程 → 重新 Upload（会全新编译，约 10~60 秒） |
