## 工作边界

- 中文沟通、中文注释
- 一次只做一个可验证的小功能；需求不明确先提问，不替用户拍板
- 不擅自引入未批准的技术（FreeRTOS/LVGL/USB CDC 各自到对应 Phase 才引入）
- 不删除 / 重命名 / 移动现有文件，除非明确要求
- 受保护目录约束：桌面下已存在文件不可改/删，新文件可建；改 doc/ 下硬件资料前先确认

## 文档更新规则

| 场景 | 更新文件 | 方式 |
|---|---|---|
| 做完一个功能 / Phase 推进 | progress.md | 覆盖（删过期，只留一屏） |
| 遇到并解决问题（排查 >20 分钟） | troubleshooting.md | 追加（带 T-NNN 编号） |
| 改变重要方案 / 选型 | decision-log.md | 追加（带 ADR-NNN，必写后果） |
| 顿悟 / 概念理清 | notes.md | 追加（必须用自己的话） |
| 硬件引脚 / 时钟 / 参数查实 | 对应文件待填位 | 原地填 |
| **接线变更（新接/改接/拆线）** | wiring.md | 覆盖对应小节 + 更新 §1 进度表 |

禁止：同一事实写在两个文件里。发现两处描述同一事实 = 删掉一处。

## 提交前文档检查（每次 commit 必做）

**顺序：先查文档，再提交。** 别把过时文档一起提交进去。

| # | 查什么 | 怎么查 | 典型处置 |
|---|---|---|---|
| 1 | **过时** | 本次改动是否让某文档的陈述不再成立？ | 更新 `progress.md` 的 Phase 状态 / 可运行状态；`decision-log.md` 补 ADR |
| 2 | **冗余** | 同一事实是否出现在两个文件？ | 确认该事实的**唯一权威源**，其余位置改成**引用**、删掉复述 |
| 3 | **占位** | 有没有空模板 / `<待补>` / `（待踩）` 之类僵尸占位？ | 已踩的把内容补上；未踩的保留但标明状态 |
| 4 | **僵尸文档** | 某文档是否只在创建时提交过一次？ | 考虑合并或删除 |

> 一句话判据：**新人只看这份文档，会不会被带去错误的地方？**

**各文件的维护语义（不要混用）：**

| 文件 | 语义 | 含义 |
|---|---|---|
| `progress.md` | **覆盖** | 永远只有一屏，过期内容**删掉**，不往下堆 |
| `decision-log.md` | **追加** | 只增不改，带 ADR-NNN + 日期，**每条必写"后果"段** |
| `troubleshooting.md` | **追加** | 只增不改，带 T-NNN + 日期 |
| `wiring.md` | **覆盖** | 反映当前接线事实 |
| `plan.md` / `README.md` | **重写** | 永远只反映当前状态 |

> 核心判据：**一个文件若同时被要求"追加"和"覆盖"，必然腐化**（典型症状：progress.md 变流水账）。
